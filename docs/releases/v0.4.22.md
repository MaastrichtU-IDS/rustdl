# v0.4.22 — `build_told_tables` was O(n²) in memset traffic: 6.2× conversion, 1.87× classify

**No output-visible change.** This is a pure performance release: one quadratic removed from the
front end, verified byte-identical across **1,780 completing ORE ontologies** and every curated
fixture. Downstream parsers see exactly what v0.4.21 emitted. Leading with that because the
release process asks for output-visible changes first — here, there are none to report.

## Behaviour changes (defaults)

**None.** No flag was added, flipped, or removed. The fix is a buffer reuse whose output is
identical by construction, so gating it behind a flag would only add a slower path.

## The fix

`owl_dl_core::told::build_told_tables` computes the reflexive-transitive closure of the told
subsumption graph with a BFS per class, and **allocated a fresh `vec![false; n]` on every
iteration**:

```rust
for c in 0..n_u32 {
    let mut visited = vec![false; n];   // n bytes, allocated AND ZEROED, n times
```

n allocations of n bytes, so the closure build cost **O(n²) in zeroing alone**, regardless of how
sparse the graph is. On `ore_ont_9674` (**981,148 classes**) that is ~963 GB of memset. A `perf`
profile of `tbox-stats` — parse + convert, **no reasoning** — attributed **69.74%** of self-time to
`__memset_avx2_unaligned_erms`, with `build_told_tables` the top rustdl frame.

**Confirmed by fit, not by inspection.** `convert_ms / n²` is constant to within **3.6%** across six
ontologies spanning a 1.34× range of n:

| ont | classes | convert_ms | ms/n² |
|---|---:|---:|---:|
| `9674` | 981,148 | 53,965 | 56,059 |
| `868` | 981,151 | 53,954 | 56,047 |
| `10689` | 981,148 | 53,917 | 56,009 |
| `8486` | 903,617 | 45,286 | 55,462 |
| `14459` | 847,760 | 40,075 | 55,761 |
| `16008` | 733,100 | 30,913 | 57,519 |

The cost is quadratic in the **class count**, not the file size — which is why the corpus's
*largest* file (557 MB) converted **fastest**. That inversion is what made the bucket look
inexplicable until the fit explained it.

**The fix is exact, not approximate.** `ups` receives a node exactly when that node is marked
visited (every `visited[i] = true` is immediately followed by `ups.push(i)`), so clearing the `ups`
entries restores the buffer in **O(|ups|)** instead of O(n). The BFS is untouched.

`RoleHierarchyBuilder::build` had the identical defect and got the identical fix, but
**precautionary with no measured win**: n there is the *role* count, whose ORE maximum is 11,312
(median 24), i.e. ~13 ms. It was sized before being applied so it would not be mis-sold as a
sibling of the 6.2×.

## Measured

**Conversion** (`tbox-stats convert_ms`): `9674` 53,965 → 8,675 ms (**6.2×**), `8486` 6.0×,
`16008` 5.0×.

**Classify**, single-thread, 300 s cap, all six byte-identical with exact row counts:

| ont | pre | post | speedup |
|---|---:|---:|---:|
| `10689` | 62.3 s | 31.1 s | **2.00×** |
| `868` | 63.4 s | 32.6 s | 1.94× |
| `9674` | 61.9 s | 32.6 s | 1.90× |
| `8486` | 52.7 s | 28.4 s | 1.86× |
| `14459` | 49.5 s | 27.1 s | 1.83× |
| `16008` | 40.4 s | 25.1 s | 1.61× |

Aggregate **330 → 176 s (1.87×)**.

**The win is broader than those six.** The full sweep found `ore_ont_2121` 1.82×, `11395` 1.46×,
`3377` 1.49×, `14042` 1.42×, `11110` 1.39× — none of which were targeted. That follows from the
cost being quadratic in class count, and only a full-population run surfaces it.

## Gates

**Two-arm sweep, all 1,920 ORE ontologies, 60 s cap, single-thread** (v0.4.21 vs candidate):

| | |
|---|---|
| both ok | **1,780 — identical 1,780, DIFFER 0** |
| DNF → ok | 1 (`ore_ont_10689`, 44.7 s) |
| **ok → DNF** | **0** |
| both DNF | 139 |
| aggregate wall (both-ok) | 3,272 → 3,102 s (**−5.2%**) |

**Recovery count carries its cap: ~3 recoveries at a 60 s cap.** Three slow-family members were
*already* under 60 s before the fix (`8486` 52.7 s, `14459` 49.5 s, `16008` 40.4 s), so they
contribute **zero** recoveries despite being 1.6–1.9× faster. **This does not move the 140-member
DNF tail figure**, which was censused at a different budget; the sweep's own `both DNF = 139` is
consistent with it but is not the same measurement.

Other gates: `cargo clippy --workspace --all-targets --all-features -- -D warnings` clean;
`cargo fmt --all -- --check` clean; suite **1655/0/78** over the six affected crates; **FP=0 net
PASS** — every fixture with a present oracle VERIFIED, closures exact, **MISSED=0**.

**Why no MISSED net was run.** The process requires it when trading completeness for speed. It is
not applicable here for a specific reason: **byte-identity subsumes ΔMISSED for an output-identical
transformation** — identical `classify --json` output cannot have lost a row. Had any output
changed, the MISSED net would have been mandatory.

**Sabotage-verified.** The correctness argument was tested, not assumed. Deleting the clear in
`told.rs` fails four `told::tests`; deleting it in `role_hierarchy.rs` fails `linear_chain` and
`equivalence_cycle`. Both clears are covered by pre-existing tests.

## Release-tooling fix (in `owl-reasoner-harness`)

`release-corpus-report.sh` defaulted its population to the **sentinel-free stratified 400**, while
`RELEASE-PROCESS.md` specifies the 424 (400 + 24 sentinels) and states that the 400 is blind to the
defect that motivated the verdict gate. Of the five sentinels the doc names, the default 400
contained **one**: `ore_ont_16372` (the verdict gate itself), `9347` and `5368` (the DKey
discriminators), `11085` and `10019` were all **absent**. Every release report run at the default
was therefore blind to its own gate cases — including both DKey discriminators, i.e. exactly the
area v0.4.21 changed. The default now points at the 424. Caught because the run header printed
`n=400` where the doc's baseline records 424.

### Cap-borderline ontologies (recorded so the next release does not re-litigate them)

Two ontologies in the 424 sit with their wall straddling the 60 s cap, so a single run decides
"classified" by coin toss. **Neither is a regression** — measured directly, interleaved arms, idle
host, no cap:

| ontology | v0.4.21 walls | v0.4.22 walls | output |
|---|---|---|---|
| `ore_ont_7204` | 52.9 / 54.4 / 55.0 / 63.9 / 74.0 / 78.0 / 89.7 s | 48.3 / 57.6 / 65.5 / 69.1 / 70.4 / 83.9 / 94.1 s | identical, 29,230 rows |
| `ore_ont_2574` | 60.0 / 59.3 s | **59.7 / 56.2 s** | identical, 57,851 rows (md5 `9fbb5739ef12`) |

`7204` spans ~2× on **both** binaries with byte-identical output every run (means 66.8 vs 69.8 s);
`2574` sits at ~58 s and was *faster* on the candidate in both pairs. Across three gate runs of the
same two binaries the flagged ontology **changed** (`7204`, then `2574`, then `7204`) — a lost
capability would name the same ontology every time, so the variation is itself the evidence.

The told-table fix saves ~0.1 s on `7204` (28,649 classes), far too little to decide a ~68 s wall.

### Two release-tooling defects fixed while cutting this release

Both in `owl-reasoner-harness`, both of which made the gate lie:

1. **Default population was the sentinel-free stratified 400**, not the mandated 424. Of the five
   sentinels `RELEASE-PROCESS.md` names, the default contained **one** — `ore_ont_16372` (the
   verdict gate itself), `9347`, `5368` (the DKey discriminators), `11085` and `10019` were all
   absent. Every report run at the default was blind to its own gate cases, including both
   discriminators for the area v0.4.21 changed. Caught because the header printed `n=400` where the
   doc's baseline records 424.
2. **The new confirmation pass reported EVERY loss as confirmed-lost.** `set -euo pipefail` plus
   `... | grep -q` — grep exits on first match, SIGPIPE kills rustdl, pipefail propagates 141, and
   the test takes the failure branch *despite the match succeeding*. It condemned `ore_ont_2574`,
   which classifies in 56–60 s. Fixed by writing to a file instead of piping. **A guard that always
   reports failure is indistinguishable from a working one** — new guards must be run against a
   known-good input, not only sabotage-tested.
