# v0.4.20

**Packaging-only hotfix. No reasoner change — the Rust tree is identical to v0.4.19.**

## Why this release exists, and why it is cut from the tag

The Protégé plugin has been unloadable in **every** Protégé 5.6.x since v0.4.5
(issue #63). The fix is two version ranges in `protege/pom.xml`. Nothing else needs
to ship.

`main` at the time of cutting carried ~70 unreleased commits and 13,829 insertions of
reasoner work, including a shipped default flip (`RUSTDL_PREP_DEADLINE` ON) and
completeness-affecting changes to `realize`/`classify`/`justify`. Releasing from `main`
would have put all of that on PyPI — irreversibly — behind a plugin packaging fix, and
`RELEASE-PROCESS.md` requires a corpus report and a two-arm sweep before any of it can
ship. So this release is cut from the **v0.4.19 tag** with the single plugin commit
cherry-picked on top. `main` continues toward the next full release.

## The gates

`RELEASE-PROCESS.md`'s gates exist to catch *answer changes* and performance drift. This
release changes neither, by construction rather than by measurement:

| gate | status |

| FP=0 net | **N/A** — no reasoner source changed |
| corpus report + verdict gate | **N/A** — no reasoner source changed |

| `wine` freshness canary (step 3) | **N/A** — binaries identical to v0.4.19 |

The claim underwriting every `N/A` above is checkable in one command: the complete diff
against the v0.4.19 tag is `protege/pom.xml`, `Cargo.toml`, `Cargo.lock`, `CHANGELOG.md`
and this file. No `crates/**` path appears.

## What changed

Plugin `Import-Package` now requests the guava and slf4j that Protégé actually exports:

```
com.google.common.collect;version="[18.0,34)"
org.slf4j;version="[1.7,3)"
```

bnd had inferred `[33.0,34)` and `[2.0,3)` from the *build* classpath
(`owlapi-distribution` supplies guava 33.0.0-jre and slf4j 2.x). Protégé pins guava to
18.0 in `protege-parent`, so its `bundles/` directory exports `com.google.common.collect`
at **18.0.0** and `org.slf4j` at **1.7.36** — verified identical in 5.6.6, 5.6.8 and
5.6.9. Felix reports only the first unresolved requirement, so the guava failure was
masking an identical slf4j one behind it.

Both imports come from a single embedded class, telemetry's `TelemetryXMLWriter`, whose
entire usage is `Lists.newArrayList(Iterable)`, `LoggerFactory.getLogger` and
`Logger.error` — all present in guava 18.0 and slf4j 1.7.36.

Embedding a private guava was rejected: ~3 MB, and it would stand a rival guava class
space beside the one `owlapi-osgidistribution` imports, whose exported packages carry
`uses:="com.google.common..."` constraints.

## Verification

- The built bundle's full `Import-Package` header resolved against the union of
  `Export-Package` from **all 34 bundles** in the stock Protégé 5.6.6, 5.6.8 and 5.6.9
  distributions: **no unresolved mandatory imports in any of the three**. Before the fix,
  two hard failures in each.
- `Lists.newArrayList(Iterable)` confirmed present in Protégé's own `bundles/guava.jar`
  via `javap`.
- `mvn verify -Dtest='*Test,*IT'` — 114 tests, 0 failures, smoke IT included.
- `verify-bundle-contents` gained a guard that unfolds the built `MANIFEST.MF` and fails
  if either clause is missing. It was confirmed **red on the unpatched pom** before the
  fix was applied, so it is a real regression test rather than one written to pass.

Not verified: launching the Protégé GUI and driving the reasoner. The failure being fixed
is a startup-time OSGi resolution error, which the resolution check covers directly.

## Upgrade note

Anyone on v0.4.5–v0.4.19 has a plugin that cannot load at all. v0.4.4 was the last working
one. Protégé auto-update will pull this release via the descriptor at
`protege/update.properties`; a manual install of `rustdl-protege-0.4.20.jar` works too.
