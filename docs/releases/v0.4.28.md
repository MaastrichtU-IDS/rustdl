# v0.4.28 — `DataUnionOf` stops being dropped, a role chain's range reaches the end, and the proof view stops trusting itself

Three fixes, all in the completeness/verification direction. **Every one of them changes
output on shapes where rustdl previously answered silently and wrongly** — `dropped` was
empty, `incomplete` was `false`, and the missing entailment was simply never derivable.
That is the D10 shape this project has now closed eleven times, and it is why none of the
three could have been caught by a green corpus gate.

## Output-visible changes, first

| shape | before | after | oracle |
|---|---|---|---|
| `∃p.{7} ⊓ ∀p.([0,5] ⊔ [10,15])` | satisfiable | **unsatisfiable** | Konclude |
| `∃p.{5} ⊓ ∀p.({1} ⊔ {2})` | satisfiable | **unsatisfiable** | Konclude |
| `Chain(t,u) ⊑ r` + `Range(r,F)` + `C ⊑ ∃t.∃u.A` + `∃t.∃u.F ⊑ D` | `C ⊑ D` missed | **`C ⊑ D` derived** | HermiT |
| a Protégé proof citing an axiom absent from the source | displayed | **rejected** | — |

The first three are new entailments, so a downstream consumer sees *more* rows, or a class
newly unsatisfiable — and proving a class unsatisfiable **elides** its `direct` rows, so a
row-count comparison can read these fixes as a regression. Compare the triple
(`direct_subsumptions`, `unsatisfiable`, `equivalent_groups`).

## `DataUnionOf` in a `∀`/range position was dropped whole (#42 item 1, commit `3914b1a` + PR #106)

`DataSomeValuesFrom(p, DataUnionOf(…))` always worked — it lowers to a class-level
disjunction. A union in a **universal**, range or counting position cannot be split that
way, so `data_range_dkey`'s parser chain matched nothing and the **whole axiom dropped**,
silently.

**The enumeration half is a logical identity**: `DataOneOf(a) ⊔ DataOneOf(b)` *is*
`DataOneOf(a,b)`, so `flatten_union_of_oneofs` is sound and completeness-preserving by
construction, and the flattened form re-enters the same per-datatype parser chain rather
than re-checking datatype consistency somewhere new. It unlocks the nested composite the
issue names first, `DataComplementOf(DataUnionOf(…))`, for free.

**The interval half has no such single-range form**, so the integer `DKey` bucket now
holds an `IntSet` — a union of ranges. The non-regression argument is structural, in two
halves, and both are worth keeping:

* Every operation is a **quantified lift** of the scalar `IntegerRange` operation —
  `contains` = `∃`, `disjoint` = `∀∀`, `subset` = `∀∃` — so a one-component set returns
  exactly the old answer *by construction*. Including the empty range, whose conservative
  `disjoint` is deliberately **not** "corrected": set semantics would say `∅` is disjoint
  from everything, and that is a change in the false-positive direction.
* A one-component set **encodes to the historical untagged IRI, byte-identically**, so
  every pre-existing key still interns to the same `ClassId`. Only genuinely
  multi-interval keys use the new `iset:` tag, and `ore_ont_9347` reads 113 at both arms —
  the recorded DKey discriminator unmoved.

`contains` and `disjoint` are **exact** (`A ∩ B = ⋃ᵢⱼ aᵢ∩bⱼ`), which they must be: they
drive clashes, so the direction of risk is a false **positive**. `subset` is the `∀∃` lift,
sound in the MISS direction always.

**Integer discreteness is load-bearing and does not transfer.** Normalisation merges
components that merely *touch* (`[0,5] ⊔ [6,10] → [0,10]`), valid only because the integers
have a successor — which leaves components separated by at least one absent integer and
makes `subset` exact on normalised operands too. `xsd:float` / `decimal` / `date` /
`dateTime` have no successor; they can merge only *overlapping* components and their
`subset` stays genuinely conservative. **Those five are a separate piece of reasoning, not
a mechanical follow-on.**

**Mixed enumeration/interval unions come free and are now exact, not dropped** — on a
discrete space `{v}` *is* `[v,v]`. That is what makes the all-or-nothing rule affordable
rather than restrictive, and all-or-nothing stays load-bearing: keeping the representable
half of an unrepresentable union yields a strictly **narrower** range, which in a `∀`
position manufactures a clash.

**Still dropped, deliberately:** unions carrying any member no integer interval set can
express (bare datatypes, `DataComplementOf`, other-datatype enumerations) — these drop
**whole and visibly**, `dropped` non-empty, never narrowed; interval unions over the five
dense datatypes; `DataIntersectionOf` in these positions; and qualified data cardinality
over a union, which takes a different path and which Konclude also does not call unsat.

## A role chain's range must reach the end of the chain (#84, PR #104)

`Chain(t,u) ⊑ r` + `Range(r,F)` + `C ⊑ ∃t.∃u.A` + `∃t.∃u.F ⊑ D` entails `C ⊑ D`, and
`classify` reported only `F ⊑ G` with `incomplete: false`. **Konclude misses this too**, so
the adjudication went to HermiT, which confirms it.

The issue predicted this needed "a chain-aware derivation rule, not an extras fold at
lowering time". That was half right. It **is** a fold — but keyed on the ordered **role
pair** rather than a single role. `chain_ranges[(a,b)]` = `effective_ranges[sup]` for every
declared `a ∘ b ⊑ sup`, consumed at the one site where the composed edge provably exists:
lowering `∃a.∃b.X`, where `a(x,y) ∧ b(y,z) ∧ a∘b ⊑ sup ⟹ sup(x,z)`. So `∃a.∃b.X` and
`∃a.∃b.(X ⊓ Range(sup))` are the same class — a logical identity, exactly as #81's
`∃R.B ≡ ∃R.(B ⊓ Range(R))`.

**The pair key is what keeps it sound.** Folding into `effective_ranges[u]` would be
unsound: a bare `u`-successor with no `t`-predecessor is not a `sup`-successor. The issue's
warning is respected precisely rather than worked around.

**Known residual, and it is this fix's own limit:** `chain_ranges` keys on **declared**
pairs, so a chain composed from two chains — `t∘u ⊑ r`, `r∘v ⊑ s`, `Range(s,F)` — never
forms the composed `(t,u,v) ⊑ s` key. HermiT derives `C ⊑ D`; rustdl misses it silently.
Pinned as the fixture `chaincompose.ofn`. Closing it needs a transitive closure over chain
composition, a strictly larger change.

## The Protégé proof view verified nothing (#56, PR #105)

Two surfaces made the same anti-fabrication promise and only one kept it. The
justification surface verified every axiom it displayed against the source ontology
(`verifiedAgainst` → `containsAxiom`, fail-hard); `RustdlProof.buildNode` parsed the tree
from `prove --json` and handed the cited axioms straight to the view, unguarded.

**This is not a blind copy of the justify guard**, because a proof node holds three kinds
of content and only one is verifiable: the conclusion and the intermediate premises are
**derived** and must *not* be verified, while `axioms[]` are literal source axioms and
must be. A naive "verify everything" rejects every proof — not hypothetically: a sabotage
that adds conclusion verification errors out 4 of 7 tests.

One branch a tree-walking fix would have missed: `justification_fallback` is a **plain**
minimal justification, never a laconic one, so its axioms are literal too and are verified
wholesale. `RustdlExplanationGenerator#materialize` deliberately keeps skipping the guard
for laconic justifications, because a weakened fragment is *entailed by* rather than *equal
to* a source axiom. Both surfaces now share one implementation of the check — a second copy
of `containsAxiom` is exactly how they drifted apart.

### The verdict gate reported FAIL, and the script's own confirmation pass was reasoning from contended numbers

The gate flagged `ore_ont_2574` and `ore_ont_7192` as classified → DNF, then its confirmation
pass re-ran them at a 180 s cap, measured **61.3 s** and **62.2 s**, and relabelled itself
"CAP-BORDERLINE, gate PASSES". That self-relabelling is the one this project's own record
names as a rationalization, so it was not accepted.

Adjudicated instead by the documented method — **sequential, idle host, alternating arm
order, 3 runs each**, against the binary that actually produced the v0.4.27 baseline
(matched by `binary_sha`, **not** by filename: `rustdl-v0.4.27-cand` self-reports `0.4.26`,
having been built before the bump):

## Evidence, and why the corpus is not part of it for two of the three

**`DataUnionOf` corpus reach is provably zero.** Exactly **one** of 1,920 ORE ontologies
authors a `DataUnionOf` at all (`ore_ont_5964` — a grep *superset*, since the collector is
reachable only from that construct), and its only union is
`DataUnionOf(xsd:decimal xsd:float xsd:integer xsd:long)`: bare **datatypes**, which the
collector correctly declines, leaving all 14 of its drops unchanged. So a green FP=0 net
here demonstrates **inertness, not correctness** — the standing caveat for this subsystem,
which shipped a real float/double false positive for months under a green net.

The evidence that counts is **8 canaries + 9 unit tests for the interval half, 7 for the
enumeration half, 7 for the chain fix**, plus **Konclude adjudication on 12 interval probes
agreeing 12/12** — gap interiors (`6`, `9`), inclusive boundaries (`5`, `10`), adjacency,
unbounded ends, and both mixed-union directions. Konclude **reports** the relation on 5 of
the 12, so its silence on the other 7 is a discriminating control rather than the
under-reporting it does elsewhere.

**Sabotage: 11 run across the three fixes, 10 caught first pass, 1 survived and was
closed.** The interval half: 7 for 7 — reverting the arm, loosening all-or-nothing, merging
across gaps, relaxing `subset`'s outer `∀`, relaxing `disjoint`'s, dropping the singleton
byte-identity short-circuit, and reordering the arm ahead of the enumeration flattener. The
chain fix: 4 run, 3 caught, **1 survived** — and it was the unsound variant.

## Three things worth keeping from this release

**A guard can be blind to the implementation you actually wrote.** #104's false-positive
guard used a **top-level** `∃u.A`, which `atomic_existential_rhs` handles without ever
calling `nested_extras` — so it guarded the implementation the *issue* warned about and was
structurally blind to an over-broad fold in the code that was written. Making the lookup
match any pair whose second leg is `u` left it green. Both guards are kept; they cover
different implementations of the same mistake.

**A vacuity failure's implied scope needs checking before you believe it.**
`the_detection_set_has_not_silently_gone_vacuous` failed on #104, which reads as "the fix
closed every gap in the acceptance set". A per-fixture diff against a pinned pre-fix binary
showed **exactly one of ten fixtures changed** — the target. The fix is surgical, not
sweeping.

**Two tests were pinning the interval defect, and only one was labelled.** The scope guard
said so and was flipped as instructed. `datatype_value_membership.rs`'s
`data_union_forall_union_dropped` did **not**: it asserted a class satisfiable *on the
grounds that the union drops*, while Konclude had always called it unsatisfiable — the
satisfiable verdict was the miss, not the answer. It surfaced during **sabotage testing of
a neighbouring file**, not from the fix's own suite. Flipped, not deleted.

## Perf

**+2.8% on the worst case, accepted, mechanism unknown.** The interval-set change widens
the element of `seed_bucket`'s O(k²) ordered-pair walk. **The frame that looked right was
inert:** the DKey-heavy ontologies this project names by pair volume (`1833`, `5368`,
`2504`, `4141`) are all **string** buckets with near-zero integer literals — 0.90–0.99×,
content identical. Selecting on them would have been the documented "`ore_ont_9347` cannot
discriminate" trap, one datatype over.

The discriminator is **`ore_ont_15635`** — 58,794 `xsd:integer` literals, k = 7,281 distinct
keys, the largest integer bucket in ORE. Min-of-5, interleaved with alternating arm order:
**3341 → 3434 ms, +2.8%**, content identical. `SmallVec<[IntegerRange; 1]>` was tried and
**recovers 0%** (3437 ms), which refutes the allocation hypothesis — hence a plain `Vec`,
rather than shipping a doc comment claiming a benefit the measurement had just contradicted.
