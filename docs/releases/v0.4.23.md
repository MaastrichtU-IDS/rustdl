# v0.4.23 — output-visible: a wrong `realize` type, an FP fix, and one default flip

**Read this section if you consume rustdl's output.** Unlike v0.4.22 (which was byte-identical),
this release changes what three surfaces emit.

## 1. `realize` no longer reports synthetic DKey IRIs as entailed types (wrong output, fixed)

The integer-facet data lowering mints synthetic `DKey(range)` filler classes with
`urn:rustdl-dkey:` IRIs. They live **inside** the class vocabulary, so the `< num_user_classes`
bound did not exclude them and the unsatisfiable filter did not either — a `DKey` could be reported
as an entailed type of a named individual.

**Observed, not theoretical:** on `ore_ont_16372`, `realize` reported `urn:rustdl-dkey:f:*:e:*:e`
for **23 individuals — 23 of 23 type pairs, i.e. 100% of that ontology's realize output** — in both
`types` and `direct_types`. Now 0.

This closes the hazard #68 documented and could not reproduce; the reproducer came from grepping
~1,250 `realize --json` outputs already on disk from an unrelated bake-off. Guard applied at all
three sites **after** `.enumerate()`, since filtering the id space before it would reintroduce
exactly the aliasing bug #68 fixed.

## 2. `classify` DKey id-aliasing false positive (#67, #68)

Report positions were being used as `ClassId`s. Merged from parallel work; validated by a two-arm
differential over **663/663 data-property-bearing ORE ontologies: 0 DIFFER, 0 REGRESSION,
0 RECOVERY**, re-measured after rebasing onto v0.4.22. See
`docs/dkey-id-aliasing-fix-resolution.md` and `docs/2026-08-22-dkey-reportedclasses-differential.md`.

## 3. NEW FIELD: `realize --json` reports `witness_prune_active`

`true` iff the pseudo-model witness prune was applied, so some reported **non**-memberships were
*skipped* rather than refuted. Additive, so `schema_version` stays `1` (same convention as
`incomplete`'s addition in `2c5227d`).

**Why it exists.** That prune can discard a genuinely entailed type and did so **silently** —
`incomplete` stays `false` because no probe is cut, the prune simply never asks. A count would be
useless (the prune fires on most non-types, which is why it is worth 2.4× more completions), so the
signal is the boolean "this approximation was in play". `false` means every reported non-membership
was actually refuted.

## Behaviour change (defaults)

| flag | change | effect |
|---|---|---|
| `RUSTDL_INVERSE_FUNC_MAX` | **OFF → ON** | `realize` no longer drops inverse-functional-forced individual equality |

`=0` reverts. The fixture goes `x:[A]`,`y:[B]` → `x:[A,B]`,`y:[A,B]`.

**What unblocked a flip that was measured-and-rejected on 2026-08-18: a consumability gate, not
more budget.** The three ontologies that blocked it (`ore_ont_9662`, `7532`, `9786`) carry **8**
`InverseFunctionalObjectProperty` each and **zero** `ObjectPropertyAssertion` — so the emitted
`∃r⁻.⊤ ⊑ ≤1 r⁻.⊤` GCI put an `at_most` on eight inverse roles across 288–484 existentials for a
merge that could never fire: **19× / 47× / 31×** slowdowns. That also confirms the previously
*unmeasured* mechanism hypothesis — cost scales with the count of such roles (`ore_ont_13859`, with
one, showed no slowdown). Emitting only for roles that occur in an `ObjectPropertyAssertion` — the
only shape in which the merge can fire, the same pattern as `RUSTDL_DKEY_MERGING_GATE` — removes all
three (**1.00× each**).

**Framed honestly: a correctness fix with ZERO measured corpus benefit and zero measured cost** —
the same basis on which its functional sibling already ships default-ON (recorded as firing on 0 of
64 qualifying ORE ontologies). **Do not cite it as a corpus win.** The gate deliberately forgoes
`ore_ont_13859`'s classify gain (+3 direct rows, the "+17 closure" in the design record), which also
has no `ObjectPropertyAssertion` — a TBox-side gain that arrived bundled with a classify-side cost
19–47× larger on more ontologies.

Two record corrections found while re-verifying: those three no longer DNF at 120 s as documented
(they complete at 26–89 s, from v0.4.22's conversion fix), and `9786` was both a gainer and a
slowdown, which was unnoted.

## Performance

`derive_disjunction_existentials` now hands its told tables to `derive_forced_disjuncts` when it
appended nothing, so the immediately-following rebuild is skipped. `build_told_tables`' axiom scan
is O(#axioms) with a pool lookup each — **3.9 s per call** on `ore_ont_3524` (2,097,631 axioms),
where the BFS it precedes costs 114 ms. Conversion 19,656 → 16,528 ms (1.19×); classify `3524`
22.20 → 19.19 s, `9674` 32.81 → 29.27 s. Narrow by construction: it helps only axiom-heavy TBoxes
and is inert elsewhere.

Behaviour-identical, so unflagged: the tables are reused **only** when `axioms.len()` is unchanged,
and every mutation in that pass sits inside a loop that pushes an axiom.

## Known limitation, narrowed not closed

The pseudo-model prune's falsified soundness argument is **not** retired. Only the
inverse-functional arm is fixed. Measured with the new default ON: `ore_ont_10009` still loses 2
types (`ObjectMaxCardinality`/`ObjectExactCardinality`) and `ore_ont_3892` — real-world, Semantic
Web Dog Food — still loses 3 with **no merge construct at all** (21 `ObjectUnionOf` + 171
`DisjointClasses`, lost by case analysis). The general failure stands: a `Sat` completion is a
**pre-model** whose labels hold only what one branch was forced to derive.
Corpus frequency: 8 ontologies, 17 (individual, type) pairs of **8.41 M**.
See `docs/known-limitations/realize-drops-derived-individual-equality.md`.
